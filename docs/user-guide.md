## Setup

### Manual install

The README's installer does all of this. By hand, from your clone:

```bash
uv tool install --editable .
claude auth login
```

`--editable` runs this repository's code directly, so pulling updates needs no reinstall. It
installs `delivery` and `coordinator` (`coordinator <command>` is `delivery <command>`). Without
uv: `python3 -m venv .venv && . .venv/bin/activate && python -m pip install -e .`

The supervisor uses only your Claude subscription login. It refuses to run if an API key,
`ANTHROPIC_AUTH_TOKEN`, `apiKeyHelper`, a Bedrock/Vertex/Foundry setting or a non-default
`ANTHROPIC_BASE_URL` would take over billing; there is no paid fallback.

The application lives in **its own** repository. The supervisor never touches your working
checkout: it keeps its own clone and a separate worktree per run.

### The config file

`delivery setup` writes `~/delivery.local.toml`. By hand, start from `delivery init --config
~/delivery.local.toml`. Commands read that file unless you pass `--config <file>` or set
`DELIVERY_CONFIG`. It is fully commented; the important values:

| Setting | Value |
|---|---|
| `identity.developer_jira_account_id` | Your Jira account ID (`delivery credentials check` shows it) |
| `jira.base_url`, `project_key`, `email` | Your Jira site, project and Atlassian email |
| `jira.supported_issue_types` | Only issue types that carry the delivery workflow |
| `repository.url`, `base_branch`, `checkout_path` | The application repository |
| `repository.worktree_root`, `runtime.state_dir` | Local folders **outside** any Git checkout |
| `approvals.jira_account_ids`, `github_logins` | Who approves, and the independent GitHub reviewer (empty: anyone) |
| `checks.*` | The application's real gates and CI job names |
| `claude.model`, `[claude.models]` | Model for every procedure, with per-procedure overrides |
| `[claude.interactive]`, `[preview]` | Optional: [watch Claude](#watching-claude-and-trying-the-change) in tmux; run the app in your browser |
| `[figma]`, `[jira.attachments]`, `[notifications]`, `[reminders]`, `jira.linked_projects` | Optional |
| `[workflow.statuses]`, `jira.fields.resume_stage` | Generated by `delivery workflow inspect` |

Secrets never go in this file. There is no limit on concurrent tickets: every eligible ticket
assigned to you runs.

**Sharing the team's settings.** Most of the config is the same for everyone on a project. The
first developer writes it to a project file (no secrets, nothing personal):

```bash
delivery project export projects/SDLC.toml
```

Commit it under `projects/`. Everyone else runs `delivery setup` (it offers those files) or
`delivery setup --project <file>`. A value in your own config wins over the project file.

### Authentication

- **Jira**: create an API token at https://id.atlassian.com/manage-profile/security/api-tokens,
  then `delivery credentials set` (macOS). It checks the token with Jira and stores it in your
  Keychain. `delivery credentials check` re-tests it; rerun `set` after rotating. On
  Linux/WSL2, `read -rs JIRA_API_TOKEN && export JIRA_API_TOKEN` in the shell that runs the
  supervisor.
- **GitHub**: the supervisor uses your `gh auth login` session.
- **Figma** (optional): `delivery credentials set figma`.

Claude sessions never receive the Jira, Figma or GitHub tokens, your SSH agent or your Git
credentials.

### Map the workflow and check

```bash
delivery workflow inspect
```

Paste the `[workflow.statuses]` and `[jira.fields]` block into your config (setup does this for
you). Once per project, or after changing the workflow, prove every route:

```bash
delivery workflow verify --yes
```

It creates two unassigned test tickets labelled `delivery-workflow-check`, walks them through
every status and reports missing or unexpected transitions. Delete them afterwards. Then:

```bash
delivery doctor
delivery doctor --claude-probe
```

`doctor` is read-only: Jira identity and approvers, status mapping, repository access, branch
protection, Git push, Claude version and auth, plugin, Figma token. Fix every `FAIL`.
`--claude-probe` (once per machine; uses a little subscription usage) proves a worker session
cannot read a planted secret, push, write outside its directories, use `gh` or reach the
network. `coordinator --dry-run` lists what would start without doing anything.

### Running the supervisor

`coordinator` starts `delivery run` in a tmux session and shows it. Closing the window or
`Ctrl-b d` only detaches. Without tmux (`brew install tmux`) it runs in this terminal;
`coordinator --foreground` does that on purpose. Options: `--config <file>`, `--dry-run`,
`--once` (run eligible tickets to completion, then exit), `-v`.

It polls every 60 seconds, including for tickets that became ready while you were offline. Run
one supervisor per Jira identity; a second on the same machine is refused.

`coordinator stop` (or `Ctrl-C`) checkpoints every session, and they resume next start.
`coordinator restart` picks up new coordinator code; a running one says when the code on disk is
newer. Its output is kept in `coordinator logs`.

Each stage start and finish prints a block with the ticket, status change, Claude procedure and
model, outcome, your next step and a Jira link.

## Working a ticket

### Submit

Create the ticket in **Backlog** with a real brief: problem, scope and exclusions, numbered
acceptance criteria (`AC1`…), constraints, links and open questions. Assign it to yourself and
choose **Submit for refinement**. It stays yours while assigned to you, whoever moves it.

Jira holds decisions only. Every comment that waits for you starts with the action to choose and
the status it moves the ticket into. Check results are not posted (only failures are named).
Specifications, plans, reviews and release documents are versioned on the `delivery/<KEY>`
branch of the application repository; comments link to exact commits.

Comments are deliberately terse, so what applies to every ticket lives here rather than in them:

- Anyone allowed to decide can make the move (see `[approvals]`); the comment does not name them.
- A request-changes move takes your comment with it, and PR review conversations that are still
  unresolved are included. Without a comment Claude asks what to change.
- **Submit implementation changes** after a failed verification fixes every R- and F-item (say
  `only F2 and F3` to narrow it). **Submit follow-up changes** re-verifies the same candidate
  without new code, which only helps when a flaky check or a change on the base branch caused the
  failure.
- The coordinator never merges or deploys. After **Approve release**, you merge the PR; the merge
  is the release and the coordinator records and verifies it.
- A new commit on a PR needs verifying again before its code can be approved.
- Deviations nobody names in a change request are accepted when the code is approved.
- The acceptance comment links the acceptance guide (how to check each criterion by hand); the
  criteria themselves are in the ticket.
- How a release was merged (merge, squash or rebase) and the run behind each comment are in the
  release verification report and `coordinator logs`, not on the ticket.

### Designs and attachments

Attach designs, screenshots or documents to the ticket (or paste images into the description).
The coordinator downloads them with your Jira login and gives them to Claude as read-only input.
Only images (PNG, JPEG, GIF, WebP), PDFs and plain text are handed over, within the
`[jira.attachments]` limits; anything else is listed as skipped. Adding or replacing one counts
as a change to the brief. Attachments are never committed, but Claude's documents describe them,
so don't attach confidential designs to tickets for a public repository.

**Figma.** Create a personal access token (Settings > Security > Personal access tokens) with
only **File content: Read-only** and **Current user: Read**, and store it with `delivery
credentials set figma`. In Figma, select a frame, right-click, **Copy link to selection**, and
paste it into the ticket *description* (not a comment), one per line with a note. A page link
includes its top-level frames; whole-file links are skipped. The Figma for Jira Designs panel is
not read.

Claude gets a PNG, a summary (text, typography, colours, spacing, components) and layer data per
frame, up to `[figma] max_frames` (10). Refinement pins the Figma version; later stages use it.
If someone changes a frame afterwards, the ticket gets a "Design changed in Figma" comment and
work continues on the approved version; choose **Revise scope** to adopt the change.

### Answer questions and request changes

You decide by moving the ticket; comments are what you want to say, in your own words.

- **Questions**: reply in a comment, then choose **Submit refinement answers**. A comment alone
  never restarts work.
- **Changes**: choose **Request specification changes** (or plan, code, acceptance, release) and
  say what to change in a comment, before or after the move. Everything written since the
  revision was posted reaches Claude. See [human-templates.md](human-templates.md).

**FOR CLAUDE.** A comment whose first line is `FOR CLAUDE` (or `FOR CLAUDE development`, any
stage name, to aim it at one stage) is given to every later session of that stage. `FOR CLAUDE
project` adds it to the project's guidance file (`docs/delivery/guidance.md` on the
`delivery/guidance` branch), which every session on every ticket reads. `delivery guidance`
shows it; `delivery guidance add "<text>"` adds to it.

**PR review comments count.** On **Submit implementation changes**, the PR's unresolved review
conversations and written reviews since the candidate was published reach development as `G1`,
`G2`… items. Resolve a conversation on GitHub to leave it out.

**What Claude sees:** the description, attachments and Figma frames, what people wrote since the
step it follows from, the items to address, `FOR CLAUDE` notes from the assignee or an approver,
the project guidance, and Jira-linked tickets (summary, status, description and, if delivered,
their approved specification, plan and PR). Older comments and the coordinator's own are never
sent.

### Approve, review, accept and release

A decision is the Jira move alone, made after the revision was posted by someone allowed to
decide. No comment is needed.

- **Specification and plan**: choose the approve action. If a kept-open session published a newer
  revision, the move approves that one.
- **Code review**: an independent human approves the PR on GitHub at the current head with CI
  passing, then you choose **Approve code**. A new commit needs verifying again.
- **Deviations**: if development differed from the specification, the review lists it (`D1`…)
  and asks whether it is acceptable; it never fails verification. Approving the code accepts it,
  and the specification is rewritten to include it. Otherwise choose **Request code changes**,
  say `D1: keep to the specification`, and choose **Submit implementation changes**.
- **Acceptance**: the ticket comment links the acceptance guide (how to check each criterion by
  hand) and `delivery try <KEY>`. With `[preview]` configured your coordinator also runs the
  candidate in your browser. Then **Accept delivery**, or **Request acceptance changes**.
- **Release**: approve the proposal, then merge the PR on GitHub. The merge is the release: the
  coordinator reads the merge commit, verifies it contains the approved candidate (merge, squash
  or rebase) and moves the ticket to Done. Nothing to record by hand.

## Several tickets at once

- Eligible tickets run concurrently, each with its own worktree, branch, ports, logs and session.
- Each plan publishes a **change footprint**. The supervisor compares footprints of every
  in-flight ticket in the project, including other developers', and warns on both tickets about
  an overlap. Overlaps never pause work; shared interfaces, schemas, migrations and "is blocked
  by" links are flagged higher risk. Detection is advisory: it cannot see unpublished work.
- Verification tests your candidate alone and merged with the latest base and interacting
  candidates.
- A textual merge conflict is **flagged, never a failure**. Resolve it in the PR when you merge.
  Alternatively, every development run on an existing branch first merges the latest base, and a
  short Claude session (`resolve-conflicts`) resolves conflicts; if it cannot, the conflict stays
  flagged. `[flow] resolve_conflicts = false` turns this off.
- If a candidate waiting in Code review or Acceptance review goes out of date, the ticket says so
  once and how to verify again on the latest base (**Submit follow-up changes**).

`delivery team` lists every in-flight ticket in the project, grouped by what it waits on, longest
wait first. Your coordinator also comments on your tickets that have waited long for a person
(`[reminders]`: `after_hours` 24, `repeat_hours` 24, `max_reminders` 3, `weekdays_only`, and an
optional Slack `webhook_env`; `after_hours = 0` turns it off).

## Watching Claude and trying the change

### Reading what Claude did

`delivery logs PILOT-123` shows the latest run: what Claude said, each tool it used, anything
denied, how it ended. Options: `--follow`, `--list` (all runs), `--stage <name>`, `--run <id>`,
`--results` (tool output), `--raw` (paths to the stream-JSON files). `coordinator open PILOT-123`
opens the readable copy (`--folder`: the run folder, `--jira`: the ticket). `coordinator logs`
without a ticket shows the coordinator's own log.

### Asking Claude what is wrong

```bash
coordinator help PILOT-123 "I approved the plan an hour ago, why hasn't development started?"
```

It gathers a briefing (what `inspect` explains, Jira comments and history, what the coordinator
is doing, this machine's runs and logs), then opens Claude in this terminal with it. Claude says
what is happening and what to do; ask follow-ups, `/exit` ends it. It is your own Claude
session, not a sandboxed stage: read-only commands run freely, anything that changes something
is only proposed and Claude Code asks first. It never posts to Jira or sees your token. It uses
Opus unless `claude.help_model` is set; `--briefing-only` just writes the briefing.

### Resolving a blocked ticket with Claude

On a Blocked ticket assigned to you, choose **Request resolution** (needs the optional statuses
in [jira-workflow-setup.md](jira-workflow-setup.md) and `[claude.interactive]`). A Claude session
opens in a terminal window in the blocked stage's working copy, reads the blocker, run result
and logs, fixes what it can, and asks you in the session where a choice is yours. When it
finishes, the coordinator:

- posts **Blocker resolved**: the cause and a table of every decision with who made it (a
  decision attributed to you is kept as yours only if you answered or typed to it), and
- moves the ticket back to the blocked stage's Ready status, which restarts it with those
  decisions as a note.

If Claude cannot clear it (for example it needs a scope change or a credential), the comment says
**Blocker not resolved** and the ticket returns to Blocked. It never changes the approved
specification or plan to make a blocker go away.

### Interactive sessions

By default sessions run as `claude -p`. Turn on interactive sessions and each runs as a normal
`claude` in tmux, with a terminal window opening on it so you can watch and type to it (your
message is picked up after its current step; `Esc` interrupts; closing the window only
detaches).

```bash
brew install tmux
```

```toml
[claude.interactive]
enabled = true
```

The restrictions are the same as print mode, and the coordinator still only accepts a
schema-checked result file. Claude Code's trust prompt for each new worktree is answered yes for
the coordinator's own worktrees under `worktree_root` only.

**Sessions stay open after the work** so you can keep asking about it. In a development session,
each time Claude finishes a reply with the code changed, the coordinator pushes it as the next
candidate (Claude never pushes), says so in Jira and moves the ticket to **Ready for
verification**; earlier approvals no longer count. This applies while the ticket is in Ready for
verification, Code review, Acceptance review or Changes requested and no run is working on it.

**Verification waits until you end the development session**, so a series of small changes costs
one round of review rather than one per change. Type `/exit` (or `delivery close <KEY>`) when
done: any unpushed change is pushed, then review and verification start on the next poll.
Closing the window does not end the session. This needs three **Submit follow-up changes**
transitions in Jira, from Code review, Acceptance review and Changes requested to Ready for
verification.

Specification, plan and release-proposal sessions work the same way: each reply that changes the
document is published as the next revision for review, and the next approve move approves it. No
extra Jira transitions are needed.

After acting on changes you asked for in Jira, Claude lists each item and what it did and asks
whether you want anything else. If not, close the window (`delivery attach` reopens it), or
`/exit` in a development session, which starts verification.

A session also closes after `idle_close_hours` (12) idle, when a new run of the same stage
starts, or when the ticket is done or cancelled. Unpushed changes are saved as unfinished work
for the next run, or as a patch whose path the terminal prints. `keep_open = false` closes
sessions as soon as the result is handed over.

### Trying the change in your browser

```toml
[preview]
command = ["npm", "run", "dev"]
```

| Setting | Meaning |
|---|---|
| `command` | The dev server as an argument list; `{port}` is replaced by a free port (also exported as `PORT`) |
| `setup` | Run first in the worktree (default `checks.setup`; `[]` for nothing) |
| `seed` | Run after setup, before the app, e.g. to load demo data |
| `url` | Where it answers (default `http://localhost:{port}/`) |
| `open_browser` | `false` to only print the address |
| `acceptance` | `false` to not run the candidate in Acceptance review |

The app runs: from a development session's worktree while it is open (changes show as Claude
makes them; `/exit` stops it); during Acceptance review, running the exact code-approved
candidate until the ticket leaves that status; and on anyone's machine with `delivery try
PILOT-123`, which needs only the delivery tools and the team's config (`--ref` runs another
branch or commit; `Ctrl-C` stops it). `delivery preview PILOT-123` reopens or restarts a running
app; `delivery attach PILOT-123 --procedure preview` shows its output. It runs as you, outside
Claude's sandbox, without your credentials ([security boundary](security-boundary.md)).

## Other kinds of work

Chosen by issue type or label (`[flow]` in the config):

| Kind | How it differs |
|---|---|
| **Bug** (`bug_types`, default `Bug`) | The specification records steps to reproduce, actual and expected behaviour. Development writes a failing regression test first. Verification runs the test on the base branch *without* the fix and reports whether it fails there (**Bug reproduced**), passes anyway, or is missing. Reported, never a failure. |
| **Spike** (`spike_types`, default `Spike`) | The specification is the question. Instead of a plan, Claude investigates and writes **findings** (answer, options, recommendation, evidence), reviewed in Plan review; **Approve plan** accepts them and the ticket goes to Done. Needs the **Complete spike** transition. |
| **Fast track** (label `fast-track`) | For small changes: refinement writes the plan with the specification and one approval covers both, so development starts with no plan review. Needs the **Use approved plan** transition. If Claude finds the change is not small, planning runs as usual. |

**Proposed tickets.** If a brief is too big for one delivery, refinement still writes the full
specification and proposes slices (`S1`, `S2`…) in its review comment; a spike can propose
follow-up work too. Nothing is created until someone comments `CREATE TICKETS <token>` with the
IDs. The coordinator then creates them in Backlog, unassigned and linked, and replies with the
keys.

**Taking a release back out.** `delivery revert PILOT-123 --reason "<why>"` opens a revert PR for
the ticket's merged PR and a linked Bug for the rework. People review and merge the revert; the
coordinator never merges.

## When things go wrong

- **Limits and guardrails.** Sessions have generous limits (500 turns, 2 hours for
  implementation) and stop much earlier when stuck: the same step with the same result
  (`loop_repeats`, 6 in the last 30 steps) or no activity for `stall_minutes` (15). Set under
  `[claude]`. A stopped development session keeps its changes; after **Resume development** the
  next session continues from them, unless the specification or plan changed in between.
- **Claude unavailable.** If the login expired or the usage limit is reached, nothing is blocked:
  the run waits with its work, the ticket gets a comment, new tickets wait, and the terminal shows
  **WAITING FOR CLAUDE**. The coordinator retries every few minutes and carries on once it works
  (`claude auth login`, or the limit resetting). If Claude's API is overloaded or the network
  drops, the run retries after 2, 10 and 30 minutes; a fourth failure blocks the ticket. Jira or
  GitHub being unreachable never blocks.
- **Ticket edited mid-run.** The coordinator publishes nothing from the old text and restarts the
  stage with the new text a minute later. No Resume needed.
- **Coordinator error.** The run stops, the ticket gets a comment (details in `coordinator logs`),
  and `coordinator recover <KEY> --resume` continues it. An error in a poll does not stop the
  coordinator.

## Running it unattended

- **Room**: new sessions wait while the `worktree_root` disk has under `runtime.min_free_disk_gb`
  (5) free or macOS reports critical memory pressure. Running sessions continue.
- **Sleep**: the Mac is kept awake while sessions run (`runtime.keep_awake`). Closing the lid
  still sleeps it; interrupted work resumes on wake.
- **Claude Code updates**: when `claude --version` changes, new sessions wait while the sandbox
  probe re-runs ([operations](operations.md#claude-code-updates)).
- **Alerts**: `[notifications] webhook_env` names an environment variable holding a Slack
  incoming-webhook URL for stops, errors, waiting for Claude and low room; `desktop` shows macOS
  notifications. `operational = "operator"` keeps these notices off the tickets, for projects
  whose tickets a client reads.
- **Retention**: logs and worktrees of runs finished more than `runtime.retention_days` (30) ago
  are removed daily.

## Command reference

| Command | What it does |
|---|---|
| `coordinator` / `start` / `stop` / `restart` | Start in the background and show it / start only / stop cleanly / stop and start |
| `status` | Whether it runs (and whether its code is stale), why new sessions wait, and every session |
| `team` | Every in-flight ticket in the project, grouped by what it waits on; read-only |
| `logs [KEY]` / `open [KEY]` | Claude session log for a ticket (or the coordinator's own); open it (`--folder`, `--jira`) |
| `attach` / `sessions` / `close` | Open an interactive session / list them / end one left open |
| `help KEY ["question"]` | Ask Claude what is wrong with a ticket |
| `inspect KEY` | Why a ticket is (not) eligible, its latest run, findings and the Jira actions available now; read-only |
| `try KEY` / `preview KEY` | Run the ticket's candidate and open it in your browser / reopen the running app |
| `stop KEY` | Stop one ticket's session and keep its work |
| `recover KEY [--resume]` | Reconcile one ticket against Jira/GitHub before any retry; `--resume` continues held work |
| `handover KEY` | Checkpoint a ticket and move it to Blocked so it can be reassigned |
| `dispatch pause` / `resume` | Pause or resume new launches; running sessions continue |
| `guidance [add "<text>"]` | Show or add to the project's guidance for Claude |
| `revert KEY --reason "<why>"` | Open a revert PR and a linked Bug (asks first; `--yes` skips) |
| `clean [--older-than DAYS]` | Remove worktrees finished runs left (unpushed work saved as a patch); optionally old logs |
| `credentials set\|check\|delete [jira\|figma]` | Manage the Keychain tokens |
| `workflow inspect` / `verify --yes` | Map the Jira workflow / walk test tickets through every status |
| `project export <file>` | Write your team settings as a shared project file |

## Where things live

| Location | Content |
|---|---|
| Jira | Brief, questions, decisions, status history, run summaries |
| `delivery/<KEY>` branch | Specification, plan (or spike findings), footprint, reviews, verification, acceptance guide, release documents |
| `delivery/guidance` branch | `docs/delivery/guidance.md`, read by every Claude session |
| `feature/<KEY>` branch and PR | Implementation and tests |
| `runtime.state_dir` | Your local journal, logs, run inputs and locks (private; never in Git). The coordinator's own log is `<state_dir>/supervisor/<id>/coordinator.log` |
| `repository.worktree_root` | One worktree folder per run, removed when it finishes |
| macOS Keychain | The Jira (`delivery-jira`) and Figma (`delivery-figma`) tokens |
| `~/.delivery-platform` | The coordinator's code, from the quick install |

## Troubleshooting

Start with `delivery inspect <KEY>`: it gives every reason and finding in full, failed check
output, log locations and what each Jira action offered now does.

| Symptom | What to do |
|---|---|
| Ticket not picked up | `inspect`: assignee, status, type, label, waiting input or an existing attempt. Several statuses share a board column, so check the exact status |
| Stays paused after answering | Use the Submit answers action for the stage that asked (the Questions comment names it) |
| Approval rejected | The move must come after the revision was posted, and from a listed approver if `[approvals] jira_account_ids` is set. For code: an independent GitHub review on the current head with CI green |
| Claude keeps getting something wrong | Comment `FOR CLAUDE` (or `FOR CLAUDE development`) with guidance, then Resume or Submit as usual |
| Blocked: maximum turns or time | Raise `[claude.turn_limits]` or `[claude.timeout_minutes]` for that procedure, restart, then Resume |
| Blocked: stopped by a guardrail | It repeated a failing step or stalled; `delivery logs <KEY>` shows where. Add guidance or adjust the plan, then Resume |
| Blocked: permission or sandbox | `delivery doctor --claude-probe`; never use bypass permissions |
| Blocked, want Claude to fix it with you | **Request resolution**. If nothing happens: `[claude.interactive]` on, statuses mapped, ticket assigned to you |
| "Waiting for Claude" | Login expired: `claude auth login`. Usage limit: wait for the reset. Tickets carry on by themselves |
| Second supervisor refused | One already runs for your identity; `coordinator status` says where |
| A fix is not taking effect | It runs the code it started with: `coordinator restart` |
| "Stopped unexpectedly" or "coordinator error" | `coordinator logs` has the error; `coordinator` restarts it, `recover <KEY> --resume` continues a run |
| Branch diverged or publication uncertain | `delivery recover <KEY>` checks Jira/GitHub first and never force-pushes |
| Jira or GitHub offline | Nothing is changed; it backs off and reconciles when back. At start it retries (15s, doubling to 10 minutes) without starting work |
| Disk filling up | `coordinator clean` (`--older-than 30` for old logs) |
| A Figma link was not used | The run's `designs_skipped` lists why: whole-file link, no access, no token, or over the frame limit. A rejected token expired or lacks a scope: `delivery credentials set figma` |
| No app in Acceptance review | `[preview] command` unset, tmux missing, or `acceptance = false`. `delivery try <KEY>` runs it anywhere |
| PR review comments did not reach development | Only unresolved conversations commented on since the candidate was published count |
| `FOR CLAUDE project` note not added | Only notes from you or a listed approver count; adding retries on the next poll |
| `CREATE TICKETS` did nothing | Use the token of the revision that proposed them and IDs it proposed |
| Spike stays in Ready for development / fast-track still goes to Plan review | Add the **Complete spike** / **Use approved plan** transition ([jira-workflow-setup.md](jira-workflow-setup.md)) |

More detail: [operations](operations.md), [security boundary](security-boundary.md),
[pilot runbook](pilot-runbook.md), [design decisions](design/Implementation_Decisions.md).
