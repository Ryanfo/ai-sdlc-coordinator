# Specification: Add title search to the task list

> Provenance (ticket, revision, run, inputs) is added by the coordinator on publication.

## Problem and outcome
Users scanning the task list have to read every item to find one they already know the
title of. They need a way to narrow the list to tasks whose title matches text they type,
so they can locate a task quickly instead of scanning the whole list.

## Scope
- In scope: a text search control in the task list UI that filters the existing, already
  rendered task list by title.
- In scope: filtering the checked-in synthetic task data in `src/data/tasks.ts` (loaded via
  `App`'s `tasks` prop), consistent with how the existing status filter already works.
- In scope: combining the search with the existing status filter, since both operate on the
  same visible list and the app already supports one filter dimension (`status`).

## Exclusions
- Out of scope: external APIs or any network-backed search.
- Out of scope: authentication.
- Out of scope: deployment changes.
- Out of scope: sorting changes, pagination, or highlighting matched text (not requested).

## Acceptance criteria
- **AC1**: Given the task list is showing tasks, when the user types text into the search
  control, then only tasks whose title contains that text, matched case-insensitively, are
  shown.
- **AC2**: Given the search control contains text and the list is filtered, when the user
  clears the search text, then the full list (subject to any other active filter, such as
  status) is restored.
- **AC3**: Given search text that matches no task title, when the filtered list is computed,
  then the list area shows an explicit, visible empty-results message instead of an empty
  list.
- **AC4**: Given a keyboard-only user, when they reach the search control, then it has a
  visible label associated with it and can be focused and operated using the keyboard alone.

## Non-functional requirements
- Accessibility: the search input has a visible `<label>` associated via `htmlFor`/`id`,
  consistent with the existing status filter control; the empty-results message uses
  `role="status"` (or equivalent live region) consistent with `TaskList`'s existing no-match
  message, so assistive technology announces it.
- Performance: filtering runs client-side over the in-memory fixture list (12 items); no
  specific performance target beyond remaining responsive on each keystroke.
- No new runtime dependencies (per guardrails) — implement with existing React state and the
  domain filtering module.

## Constraints
- Architecture: new query behaviour must extend `TaskQuery` in `src/domain/filter.ts`
  (`docs/architecture.md`), not add ad-hoc filtering logic inside components.
- Coding standards: TypeScript strict, pure named functions in `src/domain/`, thin
  components, no array-index React keys, errors handled at boundaries only, no lint/type
  suppressions (`docs/coding-standards.md`).
- Testing policy: unit tests for the new domain filter function (including empty input, case
  handling, and combination with the status filter), component tests for user-visible
  behaviour through roles/labels including keyboard use, and the Playwright end-to-end
  journey should cover the main search flow (`docs/testing-policy.md`). Each AC must map to
  at least one named test.
- Data: synthetic fixture data only, no real personal data (`docs/guardrails.md`).

## Dependencies
- Existing `filterTasks`/`TaskQuery` in `src/domain/filter.ts` and the `App`/`TaskList`
  components, which this feature extends rather than replaces.
- Existing status filter and its "no match" pattern in `TaskList.tsx`, which the search
  empty-results message should follow for consistency.

## Assumptions
- Search filters by substring match (contains), not exact match or prefix-only, since the
  brief says "find a task quickly" without specifying match style and substring is the
  common interpretation for this kind of control.
- Search combines with the existing status filter using AND (a task must match both the
  current status filter and the search text), consistent with `TaskQuery` already
  representing a single combined query.
- The search control filters live as the user types (no submit button or debounce
  requirement specified), consistent with the existing status `<select>` filtering
  immediately on change.
- Search is scoped to the current, already-loaded fixture list only; no cross-session
  persistence of the search text is required (unlike starred state, which is explicitly
  persisted today).

## Open questions
- **Q1**: Should title search also match against task description text, or title only? The
  brief marks this as an open question and does not answer it. It is material because it
  changes AC1's matching behaviour and could add a new acceptance criterion; a reasonable
  default, if needed, would be title-only (matching the ticket summary "Add **title**
  search") with description search left for a future ticket.
