# Implementation plan: Add title search to the task list

> Provenance is added by the coordinator. Implements the approved specification revision named in the provenance.

## Approach
Extend the existing single-query filtering model instead of adding parallel filtering logic.
`TaskQuery` in `src/domain/filter.ts` gains a `search` field alongside the existing `status`
field, and `filterTasks` ANDs a case-insensitive, title-only substring match into the same
pass it already does for status. `App` adds a second controlled input (a labelled text box)
next to the existing status `<select>`, holds its value in state the same way `status` is
held, and passes both into one `filterTasks` call. `TaskList` is unchanged: it already renders
an explicit, `role="status"` empty message whenever the filtered list it receives is empty,
regardless of which filter caused that, so it already satisfies AC3 for the search case.

## Affected files
| Path | Change |
|---|---|
| `src/domain/filter.ts` | modify — add `search` to `TaskQuery`, extend `filterTasks` to AND a case-insensitive title-substring match |
| `src/domain/filter.test.ts` | modify — update existing calls for the new required `search` field, add unit tests for case-insensitivity, title-only matching, empty search, and combination with `status` |
| `src/App.tsx` | modify — add search state, labelled text input, wire into the existing `filterTasks` call |
| `src/App.test.tsx` | modify — add component tests for filtering, clearing, the empty-results message on no search match, and keyboard operation |

No changes to `src/components/TaskList.tsx`, `src/data/tasks.ts`, `src/domain/task.ts`,
`src/storage/**`, or `docs/architecture/components.toml` (no new component, just new fields on
existing `domain`/`ui` surfaces).

## Interfaces and data
- `src/domain/filter.ts`
  - `TaskQuery` gains a required field: `readonly search: string`. Empty string means "no
    search filter" (matches current no-search behaviour); non-empty is compared
    case-insensitively against `task.title` only (not `task.description`), per AC1 and the
    specification's exclusion of description matching.
  - `filterTasks(tasks, query)` signature is unchanged; its filter predicate now ANDs the
    existing status check with `query.search.trim().toLowerCase() === "" || task.title.toLowerCase().includes(query.search.trim().toLowerCase())`.
  - No change to `sortTasks`, `StatusFilter`, or any exported type names — this is an
    additive field on an existing interface, not a new domain model.
- `src/App.tsx`
  - New local state `const [search, setSearch] = useState("")`, following the existing
    `status` pattern.
  - New labelled input, e.g. `<label htmlFor="title-search">Search</label>` +
    `<input id="title-search" type="search" value={search} onChange={...} />`, placed in the
    existing `.controls` block next to the status filter.
  - `visible` becomes `sortTasks(filterTasks(tasks, { status, search }))`.
- No storage format, schema, or migration changes; `search` state is not persisted (per the
  specification's assumptions — unlike starred state).
- No new runtime dependency: plain controlled `<input>`, no new package.

## Implementation steps
1. In `src/domain/filter.ts`, add `search: string` to `TaskQuery` and update `filterTasks` to
   AND a case-insensitive, trimmed, title-only substring check with the existing status check.
2. Update `src/domain/filter.test.ts`: add `search: ""` to existing `filterTasks` calls that
   don't yet pass it, then add cases for case-insensitive matching, title-only matching (a
   term present only in a description must not match), empty-string search behaving as "no
   filter", and search combined with a non-"all" status filter (AND semantics).
3. In `src/App.tsx`, add the `search` state and the labelled search input in the `.controls`
   block, and pass `search` into the existing `filterTasks` call alongside `status`.
4. Update `src/App.test.tsx`: add a test that typing into the search box narrows the list to
   matching titles only; a test that clearing the typed text (via keyboard) restores the full
   list (respecting any active status filter); a test that a non-matching search shows the
   existing `role="status"` empty message; and a test that the search input can be reached
   and operated via keyboard alone (focus + type), confirming the label association via
   `getByLabelText`.
5. Extend `e2e/app.spec.ts` with a step (or a new `test`) that fills the search box, asserts
   the list narrows to the expected count/title, then clears it and asserts the full list
   (or the active status filter's list) is restored.
6. Run lint, typecheck, unit, and e2e locally before handing off, per `docs/testing-policy.md`.

## Risks
| Risk | Mitigation |
|---|---|
| Widening `TaskQuery` to a required `search` field breaks any other caller of `filterTasks` outside the files listed here | Grep confirms the only callers are `src/App.tsx` and `src/domain/filter.test.ts`, both updated in this plan; typecheck will catch any missed call site |
| Reusing `TaskList`'s existing generic "No tasks match the current filter." message for the search-empty case could read as unclear about *why* nothing matched | Specification's non-functional requirements explicitly call for reusing the existing `role="status"` pattern for consistency; message text is already generic enough to cover both filter dimensions, so no wording change is needed |
| Combining two live-filtering inputs (status select + search text) could make keyboard/focus order confusing | Place the search input adjacent to the status control in the existing `.controls` block, each with its own associated `<label>`, matching the current single-filter layout pattern |

## Rollback implications
Pure UI/domain change with no persisted state, storage format, or schema touched — `search`
is transient `useState`, never written through `KeyValueStore`. Reverting the four/five
changed files (or rolling back the commit) fully restores prior behaviour with no data
migration or cleanup required.
